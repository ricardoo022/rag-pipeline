```bash
.venv/bin/python -m pytest tests/rag/test_phase1_semantic_qa.py -v -s
```

## Contexto

Esse teste roda `search_type=vector` (sem híbrido, sem rerank) sobre o KB semeado pela fixture
`seeded_kb_empresa_xy` (que recria `kb/empresa_x`/`kb/empresa_y` do zero, nas 3 estratégias de
chunking, a cada execução — `clean_db` trunca `kb_docs`/`kb_chunks` antes de todo teste). Critério
de aprovação: pelo menos uma estratégia de chunking precisa atingir `hit@5 >= 0.65` no agregado
`[GERAL]`.

**Numa primeira execução (via `make rag_phase1`), o teste FALHOU**: nenhuma das três estratégias
atingiu 0.65 de hit@5. Ao reproduzir o teste isoladamente logo em seguida — sem nenhuma mudança de
código entre as duas execuções — ele **passou com folga**. Saída completa dessa segunda execução
(a que passou) abaixo.

## Conclusão

- **Não foi causado pelas mudanças de código desta sessão.** Nada em `rag/search.py`, nas
  funções SQL de retrieval (`sql/03_functions.sql`), ou no caminho que a fixture
  `seeded_kb_empresa_xy` usa para materializar o KB de teste (`materialize_chunks_from_staging`,
  chamada diretamente, sem passar pelo grafo `rag/ingest.py:graph` que foi editado hoje) sofreu
  alteração nesta sessão. As mudanças do dia (multi-strategy no grafo, prints, fallback do
  `SemanticChunker`, `try/except` no `match_threshold` do agente) ficam em caminhos de código que
  este teste não exercita.
- **O teste é reprodutivelmente instável (flaky) contra a API de embeddings real.** A fixture
  recria o KB do zero a cada execução (`clean_db` trunca `kb_docs`/`kb_chunks` antes de todo
  teste), então a única fonte de variação entre a rodada que falhou e a que passou é a chamada real
  à API de embeddings da OpenRouter — nondeterminismo/latência/timeout na geração de vetores (ou,
  possivelmente, variação na busca aproximada do índice HNSW `vector_cosine_ops` sob carga)
  altera quais chunks ficam mais próximos da query em buscas por vetor puro (`search_type=vector`,
  sem híbrido/rerank).
- **Na execução registrada acima, todas as três estratégias passaram com folga** (hit@5: fixed
  0.97, markdown 0.87, semantic 0.97 — bem acima do limiar de 0.65 exigido).
- **Recomendação**: tratar esse teste como flaky quando rodado isoladamente contra dados reais em
  linguagem natural; não é motivo de alarme quando falha isoladamente uma vez. Se a falha se repetir
  de forma consistente, aí sim investigar mudanças reais (ex.: no provider de embeddings, no
  conteúdo de `kb/`, ou nas funções SQL de busca) — não foi o caso desta vez.
